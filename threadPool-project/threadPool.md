# 多线程要点

## 多线程使用

CPU密集型：受限于CPU性能，如视频编解码、加密解密、科学仿真和机器学习模型训练 （多核场景提高性能）
IO密集型：受限于磁盘、网络等外部设备的响应速度，如HTTP请求、大文件读写与日志记录、
    数据库查询和第三方API调用（多线程常用场景）

### 线程过多的隐患:
  线程创建和销毁比较耗cpu资源
  线程栈本身占用一定内存
  线程上下文切换占用cpu时间
  大量线程同步唤醒会使线程出现锯齿状负载或瞬间大负载宕机

### 线程池的模式：
**fixed模式**
线程个数固定不变，一般根据当前机器CPU核数量指定
**cached模式**
线程个数可动态增加，根据任务数量动态增加线程数量，但会设置线程数量阈值；
任务处理完成，若动态增长的线程空闲超过60S,则关闭线程，保持池最初数量线程

## 线程同步
### 线程互斥：
悲观锁：
    1. 互斥锁（mutex）:最基本的锁，unique_lock灵活锁管理
    2. 定时互斥锁（timed_mutex）:为了缓解mutex不够灵活的问题，增加了可选的等待时延。
    3. 读写锁 （shared_mutex）:有多个读线程存在的时候，可以考虑读写锁
    4. 递归锁（recursive_mutex）:共享数据存在递归调用的时候
    5. 自旋锁 （spinlock）:每个线程对共享资源占用时间非常短的情况。
乐观锁：
    1. **CAS（Compare-And-Swap）**：原子操作，比较内存值和预期值，相同才更新
    2. **版本号机制**：给数据加一个 version 字段，更新时校验版本号是否一致
    3. **时间戳机制**：更新时比对时间戳

atomic原子类型
    std::atomic<T>
    支持整型、布尔、指针、浮点等类型

### 线程通信：
条件变量（condition_variable）：经典场景：生产者消费者模型
    notify并不直接释放锁，需要退出临界区或调用 unlock()
信号量（semaphore）
    二元信号量与mutex区别: mutex只能由一个线程完成获取锁、释放锁操作，semaphore的wait和post可以处于不同线程

## 死锁条件
出现死锁的必要条件：
    互斥条件：一个资源每次只能被一个进程使用
    请求与保持条件：一个进程因请求资源而阻塞时，对已获得的资源保持不放
    不剥夺条件：进程已获得的资源，在末使用完之前，不能强行剥夺
    循环等待条件：若干进程之间形成一种头尾相接的循环等待资源关系
